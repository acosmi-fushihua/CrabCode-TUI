## 一、第一性原理裁决

“源码已合并”“标签存在”“网页写着某个版本”都不等于软件已经发布。一个可安装版本必须同时满足：

1. 签名 annotated tag 指向唯一源码提交；
2. 五个平台从该标签独立构建；
3. 每个平台的完整安装包通过事故回放、运行时生命周期、离线安装和零泄漏门禁；
4. 八项公开资产齐全，SHA-256、本地逐文件清单、GitHub attestation 与服务端 digest 一致；
5. 非 draft Release 已公开，并由 GitHub 明确标记为 `latest`；
6. `latest/download/install.sh` 与 `install.ps1` 实际解析到该 Release 的安装器。

`v1.0.23` 只满足第 1 项和部分平台门禁。run `30809360957` 最终为 `cancelled`，Publish job 没有执行，GitHub API 对 `v1.0.23` Release 返回 `release not found`。截至本审计写入时，公开 `latest` 仍是 `v1.0.22`。因此：

- 保留远端签名标签对象 `8cd7d6c2cc9ded29c84e83fcbb2c53d0a1d74bdf` 及其提交 `5afae9581ba5c5b57da80cd8635a17377c103fba`，作为不可变失败证据；
- 不删除、不移动、不强推 `v1.0.23`；
- 不为 `v1.0.23` 补建 Release；
- 所有修复前滚到新提交和新签名标签 `v1.0.24`；
- `v1.0.24` 成功前，不再重跑 `v1.0.23`，不继续消耗 GitHub CI。

## 二、失败链路与根因

### 2.1 x64 macOS：发布包选错运行时资产

`scripts/assemble-release.mjs` 为 x64 macOS 固定了 Bun `1.3.11` 的标准资产：

```text
bun-darwin-x64.zip
sha256 c4fe2b9247218b0295f24e895aaec8fee62e74452679a9026b67eacbd611a286
```

run `30809360957` 的两次 x64 macOS job 都在第一次 package runtime smoke 中复现同一结果：45 秒内 renderer context 未握手、未收到任何 frame、runtime stderr 为空，进程只能由门禁终止。这不是 `sources: []` 修复回归，而是业务事件进入 runtime 之前，Bun 自身已经停滞。

本机使用官方 `v1.0.22` x64 macOS 包做控制变量复现：包内标准 Bun 在 Apple Silicon + Rosetta 的无 AVX 环境中同样停滞，并明确输出：

```text
warn: CPU lacks AVX support, strange crashes may occur. Reinstall Bun or use *-baseline build:
  https://github.com/oven-sh/bun/releases/download/bun-v1.3.11/bun-darwin-x64-baseline.zip
```

随后只替换 Bun 为上游同版本 baseline 资产：

```text
bun-darwin-x64-baseline.zip
sha256 fb6739b08bf54550edaa7c824cd5b2dca45b6a06afef408443087a63105f6f8d
```

同一 TypeScript bundle 随即完成 renderer context、initialize、连续两轮 `/cost`、`end_session` 和退出，结果为 `2/2 success`。变量只有 Bun 资产，因此根因成立：标准 x64 Bun 要求 AVX，而 GitHub Intel macOS runner 的实际执行环境不能满足；发布组装器必须选择 baseline 兼容资产。

### 2.2 stderr：不能靠放宽门禁掩盖运行时错误

baseline Bun 在无 AVX Rosetta 环境仍会输出上面那条固定提示。直接允许任意 stderr 会让真实崩溃、密钥泄漏或兼容性错误逃逸。

修复采用双重精确授权：

1. stderr 必须逐字等于唯一已知提示，只允许无结尾、LF 或 CRLF 三种行尾；
2. 包内 `release-materials.json` 必须同时绑定 `CrabCode TUI`、`x64-darwin`、Bun `1.3.11`、完整 baseline URL 和上述 SHA-256。

任一字符变化、附加输出、平台变化、URL 变化或哈希变化都仍然失败关闭。源码态 smoke 没有包内来源材料，因此也不能借用该例外。

### 2.3 Windows：不是单纯超时，而是进程盘点算法放大

Windows 100 次回放长期停在清理门禁。原实现每次调用 `listPackageProcesses` 时：

1. 用一次 CIM 枚举系统全部 PID 和可执行路径；
2. 丢弃已经取得的可执行路径；
3. 对每个系统 PID 再启动一个 PowerShell 查询其路径；
4. 每次迭代的 promotion 等待、finally 和泄漏复核都会重复该过程。

复杂度由“每次一次系统快照”退化为“回放次数 × 清理探测次数 × 系统进程数”的 PowerShell 进程启动。统一 90 分钟 job 上限只暴露了问题；单纯提高上限会浪费更多 CI，并不构成修复。

现实现改为：一次 CIM 快照保留 PID 与路径，先用 Windows 路径语义和大小写不敏感的包内进程名集合过滤，再对少量候选做 `realpath` 与 package root 归属核验。终止前仍重新读取目标 PID 的当前可执行路径，保留 TOCTOU 防线。测试覆盖数组、单对象、空快照、大小写、空路径、非法 PID、非包进程与损坏 JSON。

### 2.4 arm64 Linux：未使用依赖把外部下载故障带进关键路径

第一次 arm64 Linux job 在 `bun install` 中因 `ffmpeg-static` 的外部 GitHub 资产返回 HTTP 500 失败。全仓搜索确认该 npm 包没有任何源码引用。Rust renderer 的真实契约是从 `PATH` 检测系统 `ffmpeg`，缺失时展示平台安装命令；发布包从未消费 npm `ffmpeg-static` 的路径。

因此该依赖没有产品价值，却增加安装期网络、上游 Release 可用性和脚本供应链风险。`v1.0.24` 从 `package.json` 与 `bun.lock` 删除它，并清理仅由它引入的传递依赖。媒体能力语义不变。

### 2.5 可复现性：纠正证据边界

workflow 对同一 job 已编译产物连续组装两次并 `cmp`，能证明“同一编译闭包的组装结果字节一致”。它不能证明两次独立编译的完整构建可复现。失败 run 的 x64 macOS 两次 attempt 也产生了不同大小和哈希的包，进一步证明两种命题不能混用。

`v1.0.24` 保留重复组装门禁，但把 step 名和错误文案改成准确的 one compiled product closure。由于复制独立构建会显著增加五平台 CI 成本，本次不伪造更强结论，也不为获得该结论重复构建。

## 三、实施清单与关联方兼容性

| 关联方 | 变更 | 兼容性裁决 |
| --- | --- | --- |
| x64 macOS 用户 | 标准 Bun 改为同版本 baseline Bun | baseline 放弃 AVX 优化以覆盖更保守 CPU；协议、版本和 bundle 不变 |
| arm64 macOS/Linux、x64 Linux、Windows | Bun 资产不变 | 不扩大其他平台二进制变更面 |
| Windows CI 与用户进程 | 单次 CIM 预过滤后再做 canonical 归属核验 | 泄漏判定、路径归属和终止前 PID 身份复核均保留 |
| 发布维护者 | 非 Windows 120 分钟、Windows 180 分钟；每十次回放输出进度 | 100 次回放不减少；超时是外层安全界限，不替代算法修复 |
| 媒体用户 | 删除未引用的 npm `ffmpeg-static` | 系统 FFmpeg 检测、提示和中途安装刷新逻辑不变 |
| `@acosmi/sdk-ts` | 继续精确锁定 `2.15.0` | 本前滚修复不改 SDK API、类型、事件或发布仓库 |
| Enterprise Gateway | 无代码变更 | `sources: []` 上游兼容修复保持原结论，本次只修 TUI 发布闭包 |
| 安装器用户 | 版本前滚为 `1.0.24` | 安装根、稳定 launcher、历史配置和会话路径不变 |

## 五、远端发布硬门禁

`v1.0.24` 只有同时满足以下事实才可标记审计最终通过：

1. 新标签是由 `crabcode-release@acosmi.com` 签名的 annotated tag，且标签、`package.json`、Cargo workspace、CHANGELOG 和提交完全一致；
2. 五个平台 build job 全部成功；
3. 每个平台 100/100 事故回放、2× successor turns、installer replay、零进程/socket/短命名空间泄漏全部成功；
4. x64 macOS 包内 Bun URL 与 SHA-256 是本审计固定的 baseline 资产；
5. 八项 Release 资产齐全，GitHub build attestation 与服务端 SHA-256 全部匹配；
6. `v1.0.24` 为非 draft、非 prerelease、`latest`；
7. 公开 `latest/download/install.sh` 查询并下载 `1.0.24`，且临时安装验证成功；
8. 发布后 main 仅做快进更新，工作树、构建目录、测试包与临时诊断目录完成清理。

任一项失败，Release 必须保持不存在或 draft，`latest` 不得切换，且只允许基于新证据前滚到更高版本，不得重写已推送标签。
