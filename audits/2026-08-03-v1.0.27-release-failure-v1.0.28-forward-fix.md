# CrabCode TUI v1.0.27 发布失败审计与 v1.0.28 前滚修复

日期：2026-08-03
范围：`acosmi/CrabCode-TUI` 开源 TUI 发布链；SDK、Enterprise Gateway 仅做兼容性边界复核
状态：根因已收敛，v1.0.28 本地实施与发布验证进行中

## 一、执行结论

`v1.0.27` 不是公开发行版。签名标签已推送且不可变，唯一 workflow run
`30860175235` 失败，publish 被跳过，没有 GitHub Release 或资产；不得删除、移动、
重跑或补建该版本。

本次失败不是 `sources: []` 协议问题复发，也不是 SDK `2.15.0`、Gateway、renderer、
TypeScript runtime 或安装器缺陷。Windows 第一轮证明：

1. launcher 在约 0.86 秒内退出 0，并输出完整、换行终止的 JSON 契约；
2. launcher 后代仍持有 stdout/stderr 管道，v1.0.27 在 500ms drain 期限后执行
   `bounded-cancel`，从而避免了 v1.0.26 的无界等待；
3. 随后的 TypeScript runtime 两轮完整成功；
4. 之后 `memory.ping` 连接同一隔离 state root 的命名管道返回 `ENOENT`；
5. 精确包进程清理完成，job 在第一轮快速失败，未消耗 180 分钟上限。

第一性原理根因是**所有权释放顺序错误**：验证器在只确认 launcher 的输出契约后，
便取消管道并释放了 launcher 观察对象；但它尚未证明由该启动链创建的稳定 Memory
coordinator 已完成后续 ping、promotion 和退出。Windows 的外层 Job/继承句柄约束是
启动环境的一部分，不能在后端生命周期仍被验证器使用时提前释放。

v1.0.28 的裁决是：完整输出契约可以解除“等待 launcher 输出”的阻塞，但不能解除
验证器对 Windows 启动所有权的保留。验证器必须持有一个显式进程观察租约，且该
所有权不依赖 stdout/stderr 当时是否已经 EOF；直到 Memory promotion、包内进程退出
均完成后才释放。仍打开的管道此后必须在独立期限内得到 EOF，且不得出现任何晚到
输出。该修复只改发布验证器及其 CI 前置门禁，不改产品协议或上游。

## 三、全链路因果审计

### 3.1 已被 v1.0.27 修复的第一层缺陷

v1.0.26 的验证器只给 `child.exited` 设置执行期限，随后无界等待 stdout/stderr EOF。
当 Windows 后代保留管道句柄时，父进程即使已退出，验证器仍可挂到 180 分钟 job
上限。v1.0.27 将执行期限与 drain 期限分离，并在第一轮 0.86 秒内暴露了后续问题。

### 3.2 v1.0.27 暴露的第二层缺陷

v1.0.27 的 open-pipe 恢复同时做了两件事：

1. 接受已经完整的 launcher 输出契约；
2. 立即取消两个 stream reader，并让 `runProcess()` 只返回 PID/文本等普通值。

第一件事正确，第二件事过早。package smoke 随后还要使用 launcher 冷启动的稳定
Memory coordinator。此时验证器已经不再保留原 `Bun.Subprocess`、pending readers 或
相关 Windows 外层所有权，生命周期顺序变成：

`launcher contract → release observer → runtime replay → Memory ping`

而正确顺序必须是：

`launcher contract → retain observer → runtime replay → Memory ping → promotion → package exit → finalize observer`

### 3.3 Windows Job 关联方

产品 supervisor 的内层 Job 使用 `KILL_ON_JOB_CLOSE | BREAKAWAY_OK`；Memory detached
spawn 明确使用 `CREATE_BREAKAWAY_FROM_JOB` 并把 stdout/stderr 写入 state log。根据
Microsoft 的 nested Job 规则，子进程从 immediate Job 开始向外 break away，遇到
不允许 breakaway 的父 Job 即停止。因此产品只能保证脱离自己控制的内层 Job，不能
假定任意外层测试宿主/Bun/CI Job 都允许完全脱离。

这不是要求修改 Memory 或放宽产品 containment。发布验证器创建了额外宿主边界，
就必须持有该边界直到自己验证完后端生命周期。该裁决同时保留生产进程树安全与 CI
可观测性。

## 四、v1.0.28 实施

### 4.1 显式进程观察租约

- launcher 只在 exit code 0、stdout 契约完整、stderr 满足约束时进入后续生命周期；
- 无论两个 stream 已 EOF 还是后代仍持管道，都显式保留 `Bun.Subprocess` 强引用；
- open-pipe 只在 stdout 已换行终止且 stderr 为空时获准继续，pending readers 不取消；
- launcher JSON 验证后继续执行 runtime、Memory ping、promotion 与包进程退出；
- 完整生命周期结束后调用 `finalize()`：要求独立 5 秒内 EOF；
- final stdout/stderr 必须与早先接受的快照逐字一致，晚到数据立即失败；
- 任一中间阶段失败，先终止经 realpath 证明属于 package root 的进程，再取消租约；
- 无效 JSON 在解析前已登记租约；promotion 已确认但进程退出超时时仍强制清理；
- timeout、非零退出、截断 stdout、非空 stderr、未经授权的 inherited pipe 仍 fail-closed。

### 4.2 诊断闭环

Memory ping/promotion 失败时，在删除隔离 state root 前同时落出：

- endpoint 与原始错误；
- 当前包所有权进程清单；
- `logs/memory-orchestrator.log` 最后 4KiB。

### 4.3 CI 配额保护

新建 `x64-win32-process-observer-preflight`：只安装锁定的 Bun 依赖并运行真实
parent/descendant inherited-pipe 测试。它必须证明：

- 父进程退出且契约完整后，延迟租约返回而不挂起；
- 即使 stdout/stderr 已 EOF，显式请求的 observer 仍保留到调用方最终化；
- 250ms 后后代仍存活，证明所有权没有被提前释放；
- 后代退出后 `finalize()` 得到 EOF；
- 截断、stderr、晚到输出、未经授权句柄与执行超时均失败；
- 超时清理不遗留夹具进程。

只有该 Windows 前置门禁与原生 Intel runtime preflight 同时成功，才分配五平台矩阵。
失败标签永不重跑；每个前滚版本最多推送一个新签名标签。
