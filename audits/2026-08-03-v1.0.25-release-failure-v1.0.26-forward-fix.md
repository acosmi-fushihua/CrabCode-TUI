## 一、审计结论

本次必须区分两个相互独立的故障域：

1. 用户最初截图中的 `sources: []` 全局停机是真实产品缺陷。来源是可选展示元数据，
   空集合不具备终止 framing、correlation、control、permission、trust 或 secret
   boundary 的权力。Gateway、SDK `2.15.0`、TypeScript 归一层和 Rust renderer 的
   分层修复仍然成立。
2. `v1.0.23` 至 `v1.0.25` 的 x64 macOS “零帧/少帧”发布失败是 smoke 观察器缺陷，
   不是已证明的 Bun AVX、模块求值、top-level await 或 dynamic import 故障。

发布 smoke 使用以下错误模型轮询子进程 stdout：

```text
Promise.race([stdout.read(), oneSecondTimeout])
timeout => continue => call stdout.read() again
```

Web Streams 的 `read()` 不会因为输掉 `Promise.race` 自动取消。旧读取仍然拥有下一块
数据的消费权；下一轮再创建读取后，协议块可能被已经无人观察结果的旧 Promise
消费。观察器于是报告零帧或停在 renderer context，尽管 runtime 已经产生并刷新
initialize 响应。

`v1.0.26` 的根因修复是：整个轮询周期始终只保留一个未决读取；轮询超时只表示
“本窗口尚无数据”，下一窗口继续观察同一个 Promise。只有该读取交付数据或拒绝后，
才允许创建下一次 `read()`。

## 三、第一性原理因果证明

### 3.1 生产者、传输与观察者必须分别取证

一个“没有看到帧”的报告至少有三类原因：

1. 生产者没有生成帧；
2. 生产者生成，但 fd/pipe 没有传输；
3. fd 已传输，但观察者丢弃或错误解析。

旧审计从观察者的空结果直接跳到第 1 类，是证据层级错误。此次通过独立阶段记录把
三层拆开：

- runtime 在约 0.42 秒完成 renderer context；
- x64 Rosetta 上模型目录初始化跨越约 2.0 至 5.0 秒，天然超过一个以上的一秒轮询
  窗口；
- `handleInitializeRequest` 正常返回；
- 约 6334 字节 initialize success frame 已进入输出队列；
- 外层流已收到该 control response；
- stdout guard 调用底层 write，返回 `true` 且 flush callback 执行；
- smoke 观察器仍只记录 renderer-context frame。

因此生产者、队列、序列化和 fd 写入均完成，丢失只能发生在观察端读取。

### 3.2 代码机制与现象一一对应

- 首帧若在一秒内到达，当前读取收到 renderer context；
- initialize 响应晚于一秒时，最早那个已经超时的读取消费它，当前读取看不到，因此
  报告“一帧后停住”；
- 原生 Intel 首次模块/模型初始化若首帧本身晚于一秒，旧读取直接吞掉首帧，因此
  报告“零帧”；
- ARM 启动较快时帧落在首个窗口内，测试通过，形成架构相关但并非架构因果的假象。

修复后，同一个 bundle、同一个 Bun baseline、同一协议夹具立即完成 renderer context、
initialize、连续两次 `/cost`、`end_session` 和退出。最终最小变更在 Rosetta x64 上
连续 `100/100` 完成，跨越此前第 1 次和第 19 次附近的失败位置。

### 3.3 被推翻的假设

| 历史假设 | 反证 | 裁决 |
| --- | --- | --- |
| GitHub Intel runner 缺 AVX，标准 Bun 无法运行 | v1.0.23 标准 Bun 在原生 Intel 能启动；v1.0.25 baseline 仍触发同类门禁失败 | AVX 不是已证零帧根因 |
| Bun `1.3.11` 模块求值缺陷 | `1.3.14` baseline 与消除入口 TLA 后仍失败 | 版本前滚不构成因果修复 |

| runtime 真正卡死 | 生产者和 fd 写入证据完整，修复观察器后同产物通过 | 推翻 |

## 四、实施与回归防线

### 4.1 唯一未决读取

新增 `createPersistentStreamPoller(reader)`：

- 第一次轮询创建一个读取 Promise；
- 超时后不清空、不替换该 Promise；
- 后续轮询继续与同一个 Promise 竞争；
- 数据或 EOF 交付后清空，再创建下一读取；
- 读取拒绝时先清空状态，再把原错误抛给调用方；
- 每次轮询都清除自己的 timer，不制造计时器泄漏。

### 4.2 回归测试

专项测试人为制造三次连续超时并断言：

- reader 的 `read()` 只被调用一次；
- 延迟 initialize frame 随后被完整交付；
- 交付后下一轮才产生第二次读取；
- rejected read 不会毒化下一轮。

该测试直接约束导致事故的并发不变量，不依赖 ARM 的偶然速度，也不以延长超时掩盖
错误。

### 4.3 变更收敛

排障期间曾加入启动阶段追踪、同步 `require` 和 stdout flush 探针。根因成立后这些
实验全部撤回。最终产品 runtime 源码与 v1.0.25 完全一致；v1.0.26 只改变发布 smoke
观察器、专项测试、仓库脚本白名单、版本和审计文档。这样不会把错误假设扩散到产品
模块加载语义。

## 七、CI 与发布裁决

1. `v1.0.23`、`v1.0.24`、`v1.0.25` 永久保留，不重跑、不移动、不补 Release；
2. v1.0.26 在本地完整门禁和签名审计通过后，只推送一次新签名 annotated tag；
3. 该标签只触发一次 Release workflow；禁止为了试错点击 rerun；
4. 原生 Intel 预检失败时，五平台矩阵不得分配，publish 不得执行；
5. Release 公开前，`latest` 保持 v1.0.22，安装器下载 v1.0.22 属于正确的远端事实；
6. 只有公开资产和隔离安装形成闭环后，main 才允许快进到 v1.0.26 发布提交；
7. 最终只清理开源 TUI 的 node_modules、dist、Rust target、下载的 Bun 控制材料、
   安装/测试包和隔离临时根；用户配置、会话、GUI 与含未提交源码的备份不删除。

截至本节所列本地证据，根因、实现和兼容性审计通过；公开发布状态仍为
`latest=v1.0.22`。这两个状态不得混写，远端授权证据形成后必须在同一审计文件追加
最终发布复核。
