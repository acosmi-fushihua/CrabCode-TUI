# CrabCode TUI v1.0.24 发布失败与 v1.0.25 前滚修复审计

- 审计日期：2026-08-03
- 审计范围：开源 TUI、发布包运行时、安装入口、`@acosmi/sdk-ts`、Enterprise Gateway、GitHub Release 链与本机残留
- 失败标签：`v1.0.23`、`v1.0.24`（均保留为不可变证据，均无公开 Release）
- 前滚版本：`v1.0.25`
- v1.0.24 流水线：`30823188010`
- v1.0.24 失败 job：`91718099186`（`Build x64-darwin`）

## 一、最终根因模型

本次事件包含两个先后暴露、必须分开治理的故障域。

### 1.1 业务事件故障：`sources: []` 不应拥有全局停机权

最初截图中的停机发生在 renderer sequence `6034`：Gateway/SDK 发送合法但为空的
来源集合，旧 TUI 将“没有可展示来源”误判为破坏流协议的全局故障，触发
`fail-closed runtime stop`。第一性原理上，来源是可选的展示元数据；空集合最多使
本轮没有引用卡片，不能破坏 framing、correlation、control、permission、trust 或
secret boundary，因此不具备停机权。

该链已在三个独立边界完成修复并发布：

| 边界 | 已落地事实 | 兼容性裁决 |
| --- | --- | --- |
| Enterprise Gateway | `acosmi/cloud-agent` main `9698993260591b67f84e2c320dbf600a1426ca7e`；本地后端产物 SHA-256 `0ac998174c6f7975fbe045c921f05fa55b9025c5e916a44c954f2daaac8ea397` | 只对来源事件做语义对齐，旧消费方 wire shape 不变 |
| 独立 SDK | `acosmi/sdk-ts` main 与签名标签 `v2.15.0` 均指向 `2f42ddb3b9d503373e143748784c22ff5888f6f4`；Release 与 npm `@acosmi/sdk-ts@2.15.0` 已公开，npm `latest=2.15.0` | 新增 `classifySourcesEvent()` 四态分类器；旧 parser、类型和消费路径不改，属于加法兼容 |
| 开源 TUI | TypeScript 归一层与 Rust renderer 独立防线均将 empty sources 处理为 presentation no-op；损坏的可选 provenance 只做本轮兼容降级 | 只有协议/权限/信任/秘密边界仍保留全局失败关闭权 |

SDK 之所以需要修改，不是让 TUI 依赖某个私有补丁，而是把跨客户端共享的来源语义
固定在行业 SDK 的权威边界，避免 Gateway、TUI、GUI 或第三方调用方各自猜测。
`2.15.0` 的 npm integrity 为
`sha512-Z3b35Im/+AwcFmyeleMfAKu12EweQrwqR5ffjTkZyxnQKfAZ5TjffemxcJobV4qh17/PiyFGg4RPEwE/qyMUHA==`。
本次 `v1.0.25` 不再修改 Gateway 或 SDK，避免扩大已经发布且验证完成的关联方变更面。

### 1.2 发布运行时故障：源码修好不等于安装包可运行

`v1.0.23` 与 `v1.0.24` 都没有成为 Release。`v1.0.24` 的签名标签对象
`f5f9453cc348f5827d829fa7369b4d5282d5c9cd` 指向
`54be4ea7c2f4854dd5c4ea5819be8a33106f32cb`。run `30823188010` 中：

- source verification 成功；
- x64 macOS job 在第一次完整 package runtime smoke 中失败；
- 包已连续组装两次且逐字节一致，大小 `78,868,275`，SHA-256
  `caa31254b6d933261f043f4efb7436aa238561245065f381a0f48436234d0e20`；
- 包内 Bun 可执行 `--version`，也能执行 smoke wrapper；只有加载完整业务 bundle 时
  45 秒内没有 renderer context、没有任何 frame、业务 stderr 为空；
- 失败后主动取消其余四个平台与 publish job，避免继续消耗 CI；run 最终
  `completed/cancelled`；
- GitHub API 对 `v1.0.24` Release 返回 404，公开 `latest` 仍为 `v1.0.22`。

因此安装器下载 `v1.0.22` 是 GitHub `latest` 的正确行为；错误在于 README 曾提前把
未产生公开资产的 `v1.0.23`/`v1.0.24` 写成“当前稳定版”。版本标签、源码提交、CI
成功、公开 Release、`latest` 与安装成功是六个不同事实，不能互相替代。

## 二、v1.0.25 的第一性原理修复

### 2.1 消除应用侧异步模块求值风险

历史 bundle 的入口以 top-level await 等待完整 runtime promise，同时入口内部通过
多级 dynamic import 初始化 renderer、参数层与业务 bootstrap。Bun `1.3.14` 官方
发布说明包含 ESM/TLA 求值与动态导入环死锁修复；这与“完整 bundle 停在第一帧前，
而 Bun 二进制和 wrapper 正常”的观测高度一致，但属于基于证据的因果推断，不冒充
栈样本直接证明。

`v1.0.25` 不再把入口模块本身悬挂在 top-level await 上：模块同步完成求值，异步
runtime promise 继续拥有全部生命周期；bootstrap reject 仍写 stderr 并以非零状态
结束进程。这样同时消除应用侧可避免的 TLA 风险，并保留失败关闭语义。

### 2.2 只升级有证据的平台运行时

仅 x64 macOS 包从 Bun `1.3.11` 前滚到官方 `1.3.14` baseline；arm64 macOS、
arm64/x64 Linux 与 Windows 继续使用 `1.3.11`。固定材料如下：

- archive URL：`https://github.com/oven-sh/bun/releases/download/bun-v1.3.14/bun-darwin-x64-baseline.zip`
- archive bytes：`26,509,145`
- archive SHA-256：`3e35ad6f53971a9834bf9e6786e2adf72b5f1921cc9a9c5fde073d2972944076`
- executable bytes：`69,173,328`
- executable SHA-256：`ea2f223e94bb2f4bf3050895113c3cf346438f6fa0501c8532284e063f72f7a0`
- license SHA-256：`2c6160ec8fb853f7e8f97d9b249e756c9b0ac44860a68b6bf4f1b0bcbc5c3741`

组装器、预检器、包内 `release-materials.json` 和 stderr 分类器共同绑定版本、URL 与
哈希。任一版本、URL、归档成员、大小、哈希或附加 stderr 变化都失败关闭。

### 2.3 原生 Intel 预检先于五平台矩阵

新 workflow 把 x64 macOS 完整 runtime 预检设为 build matrix 的必要前置：

1. 使用 `macos-15-intel`；
2. 从签名标签构建完整、闭合、release-minified TypeScript bundle；
3. 下载并二次核验上述 Bun archive 与解包后的可执行文件；
4. 连续十次完成 renderer context、initialize、两轮 `/cost`、`end_session` 与退出；
5. 预检失败则五平台矩阵完全不分配；矩阵内部启用 `fail-fast`。

预检会同时检查 CPU 型号和 Rosetta 标志。x64 进程运行在 Apple CPU 上时只能通过
显式本地控制组开关运行，结果标记为 `supplemental-rosetta-control`，不能取得
`native-intel-release-authority`。

本机 Rosetta 控制组提供了重要反证：Bun `1.3.14` baseline 在一次早期长回放以及
消除 top-level await 后的第四轮均出现零帧超时；第二次记录为前三轮成功、第四轮
超时。由于正式安装器在 Apple Silicon 选择 arm64 包，Rosetta x64 不是目标平台；
该反证不能否决 native Intel，也绝不能用来授权 native Intel。故发布裁决只接受
原生 Intel job 的连续十次结果。

### 2.4 超时证据与文档/安装一致性

- runtime smoke 仅在显式诊断开关且 macOS 超时时调用 `/usr/bin/sample`，输出限制
  64 KiB；正常运行和成功 JSON 不变。若系统拒绝采样，拒绝原因本身进入失败证据。
- 中英文 README 删除硬编码“当前稳定版”，只声明稳定版以公开 GitHub `latest`
  Release 为准；不会再宣传只有标签而无资产的版本。
- `v1.0.23`、`v1.0.24` 标签不删除、不移动、不强推，也不补建 Release；所有修复
  只能前滚到 `v1.0.25`。

## 三、关联方与兼容性

| 关联方 | v1.0.25 影响 | 明确裁决 |
| --- | --- | --- |
| SDK/Gateway | 无新代码变更 | 保持已发布 `2.15.0` 与 enterprise main，不重复发版 |
| x64 Intel macOS 用户 | 包内 Bun 前滚到 1.3.14 baseline；TUI 协议不变 | 原生 Intel 预检为发布硬门禁 |
| Apple Silicon 用户 | 安装器仍选择 arm64-darwin + Bun 1.3.11 | 不把 Rosetta x64 控制组当支持路径 |
| Linux/Windows 用户 | Bun、协议与包布局不变 | 避免无证据的跨平台升级 |
| 旧配置/会话 | launcher、安装根、状态根与稳定代际协议不变 | 原地升级，不迁移或清空用户数据 |
| 发布维护者 | 增加一个短 Intel 预检 job | 以一个短 job 阻止失败时启动五个长 job，净减少失败场景 CI 消耗 |
| README/安装器用户 | 文档不再绑定未发布版本 | `latest` 只有 Release 公开成功后才变化 |

## 五、发布裁决与不可变门禁

提交前远端事实：official main 为
`004ebfc2c1aba4af32ad2fd87f3c5dcea0bfc3bb`；远端不存在 `v1.0.25`；公开 latest
为 `v1.0.22`。本审计作出以下确定性裁决：

1. 只创建并推送一个由 `crabcode-release@acosmi.com` 签名的 annotated tag
   `v1.0.25`；不重跑旧标签；
2. 下一次 Release run 先执行原生 Intel 预检；预检失败时不得启动矩阵，不得创建
   Release，并立即基于新证据继续前滚；
3. 只有五平台 build、每平台 100 次 package replay、八项资产、attestation、服务端
   digest、非 draft/non-prerelease/latest 与隔离安装全部成功，`v1.0.25` 才算发布；
4. 发布成功后 main 只允许从 official `004ebfc...` 快进到审计后的发布提交；
5. 最终清理只删除开源 TUI 安装/测试包、构建缓存与已确认临时诊断目录；保留 GUI、
   用户配置/会话，以及含未提交源码的历史备份目录。

在以上远端事实形成前，公开安装命令继续解析 `v1.0.22` 是唯一正确状态；任何把
`v1.0.25` 描述为已发布的文案均为审计失败。
