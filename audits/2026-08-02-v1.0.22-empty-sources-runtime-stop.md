# CrabCode TUI v1.0.22 `sources=[]` 运行停机全链路审计

- 审计日期：2026-08-02（America/Los_Angeles）
- 事故会话：`2f45e2c4-cb56-4e0d-8276-f60ae485bedf`
- 事故版本：`1.0.22+7c3d8db962da`，源提交 `7c3d8db962dafe2eba0c1069a320c85d76542cc7`
- 安装入口：`curl -fsSL https://github.com/acosmi/CrabCode-TUI/releases/latest/download/install.sh | sh`
- 审计状态：根因已确认；环境清理结果见本文“清理记录”

## 一、结论摘要

本次不是下载损坏、CPU 架构错误、launcher 指错、网络断开，也不是截图中的 memory leader/follower 选举导致。

直接根因是 **TUI 的 TypeScript 与 Rust 两侧对同一个 `sources` 流事件存在相反契约**：上游在一次 `web_search` 后发出 `{"type":"sources","sources":[]}`。`@acosmi/sdk-ts 2.12.0` 的官方解析语义把空来源列表视为“没有可交付的来源事件”并返回 `null`；TUI 的 TypeScript 适配器却因 payload 已有 `type:"sources"` 而绕过该解析器，将空数组原样送入 Rust。Rust renderer 又把空数组认定为协议损坏，触发全局 fail-closed，主动终止 runtime。

这是一个可确定复现的 P1 可用性缺陷：**正常或至少应当可忽略的零结果/零引用展示事件，被错误升级为整个会话运行环境停机。**

事故还暴露出四个深层问题：

1. 跨语言事件契约由两套手写逻辑维护，语义已经漂移；
2. 可选、不可见的 provenance 展示事件与安全关键控制事件共用全局 fail-closed 处置；
3. 单元测试把 `sources=[]` 的错误处置固化成“预期通过”，且缺少真实网关帧回放；
4. fail-closed 已关闭 supervisor 后，退出流程再次 shutdown，最终 stderr 被次生的 `SDK runtime supervisor is closed` 遮蔽。

## 五、故障帧与完整调用链

### 5.1 最后一组事件

事故 metadata 的尾部为：

```text
6032 assistant / tool_name=web_search / tool_use_id=call_02_nhqFnE9CXt36DwbaMVGz0294
6033 stream_event / event_type=content_block_stop / source_index=4
6034 stream_event / event_type=sources / encoded_len=63
```

默认隐私策略没有开启 `CRABCODE_TUI_RAW_EVENT_DUMP=1`，所以磁盘上只保存 metadata。结合 direct-query 固定 envelope 与 63 字节长度，故障帧可重建为：

```json
{"type":"stream_event","event":{"type":"sources","sources":[]}}
```

该 JSON 的 UTF-8/ASCII 编码长度恰为 63 字节。截图中的 fatal reason 又精确指出：

```text
stream sources event sources is empty at sequence 6034
```

### 5.2 上游 SDK 语义

发布版固定依赖 `@acosmi/sdk-ts 2.12.0`。其 `SourcesEvent` 类型声明为普通数组：

```ts
interface SourcesEvent {
  sources: WebSearchSource[]
  session_id?: string
}
```

其实际解析器明确执行：

```ts
if (!wrapper.sources || wrapper.sources.length === 0) {
  return null
}
```

也就是说，SDK 把零来源当成“没有 sources 事件可交付”，而非致命协议错误。机器缓存中的 2.13.0 仍保持同样语义，单纯升级 SDK 不能修复 TUI 当前的绕过逻辑。

### 5.3 TypeScript 适配器绕过了 SDK 解析器

[`src/services/acosmi/client.ts`](../../src/services/acosmi/client.ts) 的 `normalizeAcosmiChatStreamEvent()` 只有在 payload **没有字符串 `type`** 时才调用 `parseSourcesEvent(evt)`；如果上游 payload 已经是 `type:"sources"`，函数直接 `return parsed`。因此显式类型的空数组没有被 SDK 过滤。

随后 [`src/services/api/queryModel.ts`](../../src/services/api/queryModel.ts) 把每个 `part` 无差别包装成：

```ts
{ type: 'stream_event', event: part }
```

`QueryEngine` 在 partial-message 模式继续把它送往 StructuredIO/Rust renderer。

### 5.4 Rust renderer 把可忽略事件升级成全局停机

[`crates/crabcode-tui/src/sdk_projection.rs`](../../crates/crabcode-tui/src/sdk_projection.rs) 对 `event.type == "sources"` 调用 `validate_stream_sources_event()`。该函数显式拒绝空数组：

```rust
if sources.is_empty() {
    return Err(format!(
        "stream sources event sources is empty at sequence {}",
        envelope.sequence
    ));
}
```

`Projection::ingest()` 把任意投影错误转换为 `ProjectionEffect::FailClosed`；`TuiApp::fail_closed()` 锁定输入并创建 `StopRuntime`；[`crates/crabcode-tui/src/lib.rs`](../../crates/crabcode-tui/src/lib.rs) 的 dispatcher 随即调用 `host.abort_nonblocking()`，supervisor 收到 `ProtocolFatal` 后终止子 runtime。

完整链路如下：

```text
web_search tool use
  -> gateway/SSE emits type=sources, sources=[]
  -> @acosmi SDK semantics: should be ignored (parseSourcesEvent => null)
  -> TUI TS adapter bypasses parser because payload already has type
  -> queryModel wraps as stream_event
  -> QueryEngine / StructuredIO forwards raw event
  -> Rust validate_stream_sources_event rejects empty list
  -> ProjectionEffect::FailClosed
  -> TuiApp locks input + StopRuntime
  -> RuntimeHost aborts supervisor
  -> entire interactive runtime stops
```

## 六、根因分析（Five Whys）

1. **为什么用户看到运行环境停机？**  Rust projection 返回 `FailClosed` 并主动 abort runtime。
2. **为什么 projection fail-closed？**  `validate_stream_sources_event()` 把 `sources=[]` 判为 malformed。
3. **为什么空数组到达 Rust？**  TypeScript 适配器只在 payload 缺少 `type` 时使用 SDK parser，显式 `type:"sources"` 绕过了空数组过滤。
4. **为什么两侧判断相反？**  同一协议语义由 SDK、应用 TS、Rust renderer 三处手写，缺少单一 schema/contract fixture 与跨层一致性测试。
5. **为什么一个引用列表能杀死整个会话？**  renderer 没有按事件安全性和可恢复性分级；不可见的 provenance 事件与安全关键控制协议共用同一 fail-closed 通道。

根因所有者不是“网络”或“memory”，而是 **应用内部跨语言适配/投影契约及错误分级设计**。

## 七、次生与系统性问题

### F-01 / P1：错误的非空不变量被测试固化

发布源码自带 `malformed_stream_sources_fail_closed_by_exact_field`，明确把 `sources=[]` 列为 malformed。审计运行该精确测试，结果“通过”；这证明事故行为不是偶发内存损坏，而是测试认可的确定性逻辑。

相邻正向测试只覆盖非空 sources，并未覆盖 SDK 的零结果语义；`normalizeAcosmiChatStreamEvent()` 在 release tag 中没有对应单元测试，也没有把真实的 63 字节网关帧送过 TS→StructuredIO→Rust 全链路的回放测试。

### F-02 / P1：fail-closed 粒度过粗

`sources` 被设计为不产生 transcript 内容的 null-rendered provenance。即使字段未来扩展或出现空数组，最安全的兼容行为也应是保留/记录并忽略展示，而不是终止已经在执行的会话。结构性危险事件仍可 fail-closed，但必须区分：

- 安全关键控制/权限/秘密边界：严格 fail-closed；
- 可选展示/provenance/未知扩展：有界记录、兼容降级、不中断 runtime；
- 明确上游 error：结束当前 turn，但不伪装成 renderer 协议损坏。

### F-03 / P2：退出阶段的二次错误遮蔽首要根因

fail-closed 路径先调用 `abort_nonblocking()`，supervisor 已终止。terminal 退出后，主流程仍调用普通 `host.shutdown()`；向已关闭 supervisor 发送 shutdown 失败，产生：

```text
Error: failed to close the direct CrabCode runtime
Caused by: SDK runtime supervisor is closed
```

主流程又先对 `shutdown` 使用 `?`，后检查 `pre_shutdown_failure`，导致进程外 stderr 的最终错误优先级错误。shutdown 应当幂等，且 root fatal 必须作为主错误，cleanup error 只能作为附加诊断。

### F-04 / P2：测试/daemon 生命周期隔离不足

生产 memory coordinator “脱离 TUI、稳定驻留”是设计行为；本次安装实例 PID 3370/3374 在 TUI 退出后仍运行并非本次崩溃根因。

但测试复用了同一 detached 模型，却没有可靠回收临时 state root 和 coordinator。审计前发现：

- 38 个来自开源 TUI 安装版、测试包或 `/private/tmp` 解包目录的 memory coordinator/child 进程；
- 13 组工作区 test package 目录、13 个 tar.gz 与 13 个 checksum，合计约 1.9 GiB；
- `/private/tmp` 下 313 个 `crabcode*`/`ccpkg-*`/`capm-*` 顶层残留，合计约 21.2 GiB；
- macOS per-user `$TMPDIR` 下 2,116 个 CrabCode 测试临时项，合计约 63.8 MiB。

这些进程多数绑定各自临时 socket，不会直接争抢本事故的生产 socket，但会持有二进制、阻止目录回收、消耗进程/内存/磁盘资源，并污染后续测试观察。

### F-05 / P2：单元测试污染真实用户诊断目录

`renderer_diagnostics.rs` 默认把 metadata 写入 `~/.crabcode/debug`，测试没有自动切换到 temp HOME/diagnostic dir。本次精确单测也向真实 `tui-renderer-metadata.jsonl` 追加了测试帧；清理阶段按审计前记录的精确文件长度恢复，并删除本次编译产生的 `crates/target`。测试应注入临时 sink，禁止访问真实 HOME。

### F-06 / P3：默认诊断不足以直接回放 fatal 帧

默认 metadata 很好地避免保存 prompt/tool output，但 fatal 现场没有记录无敏感性的结构摘要（例如 `sources_count=0`、payload shape hash）。raw ring 又必须事先设置环境变量才存在，事故后无法开启。建议在不保存内容的前提下，为 fatal 帧持久化：字段名集合、数组长度、类型、schema 版本、payload hash 与 root error chain。

### F-07 / 观察项：memory follower 文本不是根因

截图黄色 stderr：

```text
[memory-leader] leader busy — running as follower; watchdog @ 30000ms
```

来自 TypeScript Tier runner 的全局租约。审计时 `/Users/fushihua/.crabcode/.memory-rust-derived/.bootstrap-leader-lock` 指向正在运行的 Crab Code Dev worker PID 96329，因此新 TUI 作为 follower 是预期行为。它与 sequence 6034 的 renderer 校验错误没有调用链联系。桌面版的独立 orchestrator/socket 在清理时必须保留。

## 八、修复建议与验收标准

### 8.1 热修（必须同时做两层防护）

1. **TS 归一层使用一个权威语义**：只要 `evt.event === "sources"` 或 payload `type === "sources"`，都必须经过同一 parser；parser 返回 `null` 时返回 `undefined`，不要把空事件送入 renderer。
2. **Rust 韧性防护**：`sources=[]` 应作为合法 no-op/null-rendered 事件；对象/字段类型确实损坏时记录 compatibility diagnostic。对该可选展示事件不应全局 StopRuntime。

仅修改其中一层不够：TS 修复保护正常路径，Rust 修复保护历史 session、第三方/未来 runtime 与边界漂移。

### 8.2 契约治理

- 用一个版本化 JSON Schema/IDL 生成 TS 类型和 Rust validator；
- 把 SDK parser 的语义 fixtures 纳入仓库，禁止重复发明更强的不变量；
- 给事件增加处置等级：fatal / turn-fatal / recoverable / presentation-only；
- unknown optional event 默认有界保留并降级，不自动停止 backend。

### 8.3 必须新增的回归测试

| 测试 | 通过标准 |
|---|---|
| TS explicit `type:"sources", sources:[]` | adapter 返回 `undefined`/no-op |
| TS SSE-name-only empty sources | 同样 no-op，不能生成无 type payload |
| Rust exact 63-byte incident replay | `ProjectionEffect::None`，runtime 不停机 |
| 非空 sources | null-render，保留 raw provenance，不扰动 spinner/nested agent |
| 真正 malformed source object | 有界诊断；按处置矩阵决定 turn-fatal，而非默认全局 fatal |
| terminal lifecycle after renderer fatal | root reason 为主；shutdown 幂等且无 `SupervisorClosed` 遮蔽 |
| release smoke：web search 零结果 | 会话继续，可执行下一条工具调用 |
| test daemon cleanup | 测试结束后无 child、socket、temp state root 与 generation lease |
| test diagnostics isolation | 真实 `~/.crabcode` mtime/size 保持不变 |

### 8.4 发布门禁

修复版不得仅以当前错误单测“通过”为完成。至少要求：事故帧全链路回放、终端生命周期回归、一次真实或 hermetic 的零结果 web-search smoke、安装包逐文件验证和 test-process leak 检查全部通过。

## 十、最终判定

- **根因置信度：高。** 事件序列、错误文本、63 字节长度、SDK 实现、TS 绕过分支、Rust validator、fail-closed 调用链与精确单测相互印证。
