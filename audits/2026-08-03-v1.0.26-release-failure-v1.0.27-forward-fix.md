## 三、第一性原理根因

### 3.1 被破坏的不变量

一个有界子进程观察器必须分别约束三件事：

1. 被观察父进程必须在执行期限内退出；
2. 父进程退出后，stdout/stderr 必须在独立期限内完成或被观察器主动取消；
3. 执行超时时必须终止完整进程树，不能只终止父 PID 后无限等待后代关闭句柄。

`v1.0.26` 的 `runProcess()` 只约束了第一件事：

- `Promise.race(child.exited, timeout)` 在父进程退出后立即清除 timer；
- 随后无条件 `await Promise.all(stdoutPromise, stderrPromise)`；
- stdout/stderr 没有独立排空期限；
- 执行超时时只调用 `child.kill()`，然后仍无界等待两个流。

因此，只要父进程达到 execution deadline，或父进程已经退出但任一管道没有产生 EOF，
观察器就会永久停在 `Promise.all`。这个缺陷足以把本应在 30/60 秒内成功或失败的轮内
调用拖到 GitHub 的 180 分钟作业上限。

### 3.2 远端证据边界与最小根因

远端收尾日志记录 GitHub runner 终止两个 `acosmi-memory-orchestrator` 进程（PID 1068、
5724）。这证明被阻塞的某一轮已经启动 Memory coordinator，但尚未走完本验证器的
promotion 和进程退出检查；否则两个测试态进程应在轮内被回收。结合代码路径：

1. endpoint 请求有 2 秒 timer；
2. promotion 后的包进程等待有 10 秒 deadline；
3. Windows CIM inventory 单次有 15 秒同步超时；
4. 只有 `runProcess()` 在 execution race 结束后仍存在无期限的流等待。

故可唯一认定的根因是：包级验证器没有把“子进程执行”和“管道收尾”同时做成有界
状态机。旧日志不能进一步区分卡住的是 launcher 还是 runtime 调用，也不能区分父进程
是正常退出还是先触发 execution timeout。

特别复核 Windows 产品实现后确认：Memory coordinator 的 detached spawn 将 stdout/
stderr 写入状态根下的日志文件（无日志目标时写 null），并不直接继承发布验证器的
stdout/stderr 管道。因此，“远端一定是 Memory coordinator 直接持有验证器管道”不成立，
不得作为审计结论。两个残留 Memory PID 是生命周期进度证据，不是句柄所有权证据。

### 3.3 因果机制回归

新增真实进程夹具，不以 mock 布尔值替代操作系统语义：

- 父进程启动一个继承 stdout/stderr 的后代；
- 父进程写出完整换行 JSON 后立即退出；
- 后代继续存活并持有两个管道；
- 该夹具证明旧控制流在真实的“父进程已退出、后代仍持有管道”机制下会无限等待 EOF；
- 新控制流在独立 drain deadline 后取消 reader，并在严格契约成立时返回；
- 父进程不退出时，新控制流按 execution deadline 终止并在第二个 deadline 内结束，
  不被后代持有的管道拖死。

该夹具是对缺陷机制和修复不变量的真实 OS 回归，不反向声称它识别了远端的具体句柄
所有者。专项同时覆盖：完整契约可恢复、未授权管道 fail-closed、截断 stdout 拒绝、
非空 stderr 拒绝、父进程执行超时有界收尾。

## 四、v1.0.27 实施

### 4.1 双期限与完整树回收

`runProcess()` 现在分别拥有：

- execution deadline：约束父进程退出；
- stream drain deadline：约束 stdout/stderr EOF；
- Windows timeout cleanup：`taskkill /PID <pid> /T /F`；
- drain 超时后显式取消 reader，保留最多 4 KiB 尾部诊断并失败；
- 任一路径均不得把未决 reader 留给外层 180 分钟作业超时。

### 4.2 唯一兼容例外

只有 packaged launcher 可以在父进程退出码为零后接纳一次有界的“管道未正常 EOF”
恢复，且必须同时满足：

1. stdout 以换行结束，证明单条 JSON 契约边界完整；
2. JSON 随后由调用方按既有字段严格解析；
3. stderr 完全为空；
4. 随后的 Memory identity、promotion、包内进程退出和隔离检查全部成功；
5. 仅取消观察器 reader，不把该例外扩散到 runtime smoke 或 installer。

缺少任一条件均 fail-closed。这样既允许应当存活的 Memory coordinator 进入后续
ping/promotion/退出检查，也不会把截断输出或错误输出伪装成成功。

### 4.3 逐轮证据

每轮包级回放现在分别输出 start/complete，并在轮内输出：launcher start/complete（含
stdio 是正常关闭还是有界取消）、runtime start/complete、Memory ping、promotion、
包进程退出、隔离清理。未来任何超时都能定位最后一个完成的阶段。轮级输出仍为：

- `release package smoke iteration start: N/100`；
- `release package smoke iteration complete: N/100`。

不再依赖每十轮一次的粗粒度进度，也不再把轮内不同子系统混成同一个黑盒。

## 七、发布裁决

1. `v1.0.26` 标签和 run 永久保留，不重跑、不移动、不补 Release；
2. `v1.0.27` 必须先完成全仓本地测试、精确正式包组装、100 次隔离回放和泄漏复核；
3. 只有本地证据闭环后才创建并推送一个新的签名 annotated tag；
4. 新标签只允许触发一次 `Pure TUI Release`；
5. 五个平台、五份 100 次回放、publish、八项资产、checksum、attestation、server
   digest、公开 latest 和隔离安装任一不成立，均不得宣称发布完成；
6. Release 公开前，安装命令继续正确下载 `v1.0.22`；
7. 最终 main 只允许快进，不覆盖并发远端更新；审计回写使用 `[skip ci]`，不额外
   消耗 CI；
8. 完成后清理 node_modules、dist、Rust target、正式包、测试临时根与下载控制材料，
   保留用户源码、配置、会话、GUI 和含未提交源码的备份。
